# gethighandfly — инструкции для Claude Code

## Контекст
Сайт соревнований по кайтсерфингу: расписание, регистрация участников,
результаты, фото/видео. Стек — точная аналогия `../kitemuine`, плюс
функционал регистрации участников.
Полная спецификация: `docs/SPEC.md`

## Стек
- **Astro 5** (`output: 'static'` пока нет регистрации; переключить на `'server'` / гибрид при добавлении API)
- **TypeScript** strict
- **Tailwind 3** via `@astrojs/tailwind`
- **`@astrojs/sitemap` v3**
- Контент генерируется через Website Factory (`/opt/marfa/projects/website_factory/`)
- Деплой: `astro build` → Docker `nginx:alpine` → `docker compose up --build`
- Образец паттернов: `../kitemuine/` (landing-архитектура, Dockerfile, nginx.conf)

## Команды
```bash
npm install              # первый раз
npm run dev              # dev-сервер http://localhost:4321
npm run build            # сборка в dist/
npm run preview          # предпросмотр dist/ локально
docker compose up --build   # production-образ
```

## Железные правила
- `dist/` — только артефакт сборки, никогда не коммитить; в `.gitignore`
- Все тексты и копия — через Website Factory или `src/i18n/`; не хардкодить строки в компонентах
- Регистрация участников: решение о бэкенде — см. ADR-002 (не принято); не реализовывать без ADR
- Секреты (API-ключи, env) — только в `.env`, в git не попадают
- Деплой production — только с подтверждения владельца

## Как работать
- Двигаться по фазам из `docs/BACKLOG.md`, не перескакивать.
- Непонятно требование → спросить владельца, не додумывать.
- Перед коммитом: `npm run build` без ошибок.
- В конце сессии: обновить `HANDOFF.md`.

## Документация проекта
Не читай всё подряд. Выбирай по задаче:
- `HANDOFF.md` — **читать в начале сессии**; обновлять в конце
- `docs/SPEC.md` — перед задачей по логике или скоупу
- `docs/ARCHITECTURE.md` — при изменении структуры, модулей, потоков данных
- `docs/DECISIONS.md` — перед изменением ключевого решения; **дополнять** при новых
- `docs/BACKLOG.md` — чтобы понять что сделано и что дальше

## Компрессия контекста
При /compact сохраняй в порядке приоритета:
1. Архитектурные решения (никогда не сокращать)
2. Изменённые файлы и суть изменений
3. Текущий статус сборки (pass/fail)
4. Открытые TODO и блокеры по регистрации
5. Вывод инструментов — можно выбросить, оставить только pass/fail
