# Стандарт документации проектов

Единый набор файлов документации для всех репозиториев. Одинаковые имена везде.
Этот файл кладётся в корень каждого проекта — Claude Code читает его и знает правила игры.

---

## 1. Набор файлов

| Файл | Роль | Ритм обновления | Кто читает |
|---|---|---|---|
| `CLAUDE.md` | точка входа: что за проект, железные правила, карта доков | редко | загружается в **каждую** сессию |
| `AGENTS.md` | симлинк на CLAUDE.md (для Codex/Cursor/Copilot) | никогда | другие агенты |
| `HANDOFF.md` | живой снапшот: где мы, следующий шаг, блокеры, ловушки | **каждую сессию** | по требованию, в начале сессии |
| `docs/SPEC.md` | спецификация: что и зачем строим | при смене скоупа | перед задачей по логике |
| `docs/ARCHITECTURE.md` | текущая техническая архитектура | при структурных правках | при изменении структуры |
| `docs/DECISIONS.md` | журнал решений (ADR): что решили и **почему** | только дополняется | перед изменением ключевых решений |
| `docs/BACKLOG.md` | дорожная карта и прогресс по фазам | каждую фазу | чтобы понять «что дальше» |

Опционально, по мере роста проекта:
- `docs/DB_SCHEMA.md` — схема БД, ключевые связи, что нельзя трогать
- `docs/RUNBOOK.md` — деплой, рестарт, разбор инцидентов, где логи
- `.claude/commands/catchup.md` — слэш-команда восстановления контекста после `/clear`

---

## 2. Три закона

**Закон 1. Разделение по ритму обновления.**
Файл, который меняется каждую сессию, не должен лежать в одном месте с файлом,
который не менялся полгода. Иначе первый затирает второй, а второй раздувает первый.
`HANDOFF.md` — перезаписывается. `DECISIONS.md` и `BACKLOG.md` — только дополняются.
`SPEC.md` и `ARCHITECTURE.md` — почти статичны.

**Закон 2. Progressive disclosure.**
`CLAUDE.md` не содержит деталей — он содержит **карту** деталей с триггерами «читать когда».
Модель надёжно держит ~150–200 инструкций, из которых ~50 уже съел системный промпт
Claude Code. Каждая лишняя строка в CLAUDE.md — налог на каждую будущую сессию.
Предел: **200 строк**, лучше 100.

**Закон 3. Документация — это код.**
Правится в том же PR, что и изменение, которое она описывает.
Если Claude ошибся дважды в одном месте — это не проблема модели, а недостающая строка в доках.
Устаревшая строка хуже отсутствующей: она уводит агента уверенно и в неверном направлении.

---

## 3. Правила написания

- **Императив, не вежливость.** «Use Pest» работает; «мы обычно предпочитаем Pest, когда это возможно» — нет.
- **Не дублируй линтер.** Правила форматирования применяет форматтер, детерминированно и бесплатно.
  В доках только те конвенции, которые линтер проверить не может.
- **Ссылки на файлы вместо кода.** Не «вот 40 строк как работает сервисный слой»,
  а «бизнес-логика в `core/services/`, образец — `core/services/booking.py`».
- **Что нельзя трогать — пиши явно.** Границы («никогда не редактируй `migrations/`, только добавляй новые»)
  агент сам не выведет.
- **То, что обязано выполняться — делай хуком, а не строкой в CLAUDE.md.**
  Инструкции в доках — рекомендательные; хуки — детерминированные.
- **Не автогенерируй.** `/init` даёт скелет, дальше переписывай руками. CLAUDE.md — самый
  высоколевереджный файл в репозитории, автогенерация его портит.
- **Русский в текстах, английский в именах** файлов, переменных, коммитов.

## 4. Шаблоны

### CLAUDE.md

```markdown
# <Проект> — инструкции для Claude Code

## Контекст
<1–3 строки: что это и зачем. Без воды.>
Полная спецификация: docs/SPEC.md

## Стек
<Язык + версия, фреймворки, БД, инфраструктура. Только то, что нельзя угадать по коду.>

## Команды
```bash
<точные инвокации: установка, dev, тесты, один тест, линт, билд, деплой>
```

## Железные правила
- <границы архитектуры: что где лежит и что где лежать не должно>
- <конвенции, которые линтер не проверит>
- <безопасность: секреты, что не коммитить>
- <definition of done: что должно быть зелёным перед коммитом>

## Как работать
- Двигаться по фазам из docs/BACKLOG.md, не перескакивать.
- Непонятно требование → спросить владельца, не додумывать.
- Перед коммитом: <команда тестов> зелёные.
- В конце сессии: обновить HANDOFF.md.

## Документация проекта
Не читай всё подряд. Выбирай по задаче:
- `HANDOFF.md` — **читать в начале сессии**; обновлять в конце
- `docs/SPEC.md` — перед задачей по логике или скоупу
- `docs/ARCHITECTURE.md` — при изменении структуры, модулей, потоков данных
- `docs/DECISIONS.md` — перед изменением ключевого решения; **дополнять** при новых
- `docs/BACKLOG.md` — чтобы понять что сделано и что дальше

## Компрессия контекста
При /compact сохраняй в порядке приоритета:
1. Архитектурные решения (никогда не сокращать)
2. Изменённые файлы и суть изменений
3. Текущий статус проверок (pass/fail)
4. Открытые TODO и заметки об откате
5. Вывод инструментов — можно выбросить, оставить только pass/fail
```

### HANDOFF.md

```markdown
# <Проект> — HANDOFF
Обновлено: YYYY-MM-DD

## Сейчас
<Одним абзацем: на какой фазе, что только что закончили.>

## Следующий шаг
<Конкретное действие, не «продолжить работу над модулем».>

## Нужно от владельца
- [ ] <токен / доступ / решение — то, что блокирует агента>

## Ловушки
- <что уже пробовали и не сработало — чтобы следующая сессия не повторила>
- <неочевидное поведение окружения>

## Файлы в работе
- `path/to/file.py` — <что там незакончено>
```

Правило: HANDOFF пишется **для агента с нулевым контекстом**. Проверка качества —
если по нему нельзя продолжить работу, не читая историю чата, он написан плохо.
Держи в пределах экрана; всё, что завершено, уезжает в BACKLOG.

### docs/DECISIONS.md

```markdown
# <Проект> — Журнал решений (ADR)

## ADR-001 — <короткий заголовок решения>
- **Дата:** YYYY-MM-DD
- **Статус:** Принято | Устарело | Заменено ADR-XXX
- **Контекст:** <какая была проблема, какие ограничения>
- **Решение:** <что выбрали>
- **Альтернативы:** <что рассматривали и почему отвергли>
- **Последствия:** <чем платим, что теперь нельзя>
```

Когда заводить ADR: решение меняет архитектуру, эксплуатацию, безопасность
или долгосрочную стоимость поддержки. Одно решение — одна запись, не сваливать в кучу.
Записи **не удаляются и не переписываются** — устаревшие помечаются статусом
«Заменено ADR-XXX». История отвергнутых вариантов — главная ценность файла:
она не даёт агенту через месяц «улучшить» то, от чего отказались осознанно.

### docs/BACKLOG.md

```markdown
# <Проект> — Бэклог

## Статус фаз
| Фаза | Название | Статус |
|---|---|---|
| 0 | Фундамент | ✅ |
| 1 | ... | ⏳ |

## ⏳ В работе
### Фаза N — <название>
- [ ] <задача>

## Дальше
- <фаза / задача с однострочным описанием>

## ✅ Сделано
### Фаза 1 — <название> (YYYY-MM-DD, коммит `abc1234`)
<3–5 строк: что появилось, сколько тестов. Без простыней кода.>
```

Правило: завершённые фазы **сжимаются** до нескольких строк. Детали живут в git-истории,
не в бэклоге. Раздутая секция «Сделано» — тот же context rot.

### docs/ARCHITECTURE.md

Описывает **текущее** состояние (не историю — она в DECISIONS):
карта директорий и зона ответственности каждой, потоки данных,
внешние интеграции с точками отказа, схема (Mermaid), инварианты системы.

### docs/SPEC.md

Что и зачем строим: манифест и принципы, роли и сценарии,
функциональные требования, ограничения и известные факты (лимиты API, квоты, легалка),
явное «что мы НЕ делаем».

## 5. Кросс-инструментальная совместимость

Claude Code читает `CLAUDE.md` и не читает `AGENTS.md` нативно. Остальные агенты
(Codex, Cursor, Copilot, Gemini CLI, Aider) читают `AGENTS.md`. Чтобы не держать две копии,
которые разъедутся за две недели — один файл и симлинк:

```bash
ln -s CLAUDE.md AGENTS.md
```

Единственный источник правды — `CLAUDE.md`.

---

## 6. Гигиена сессии

**Начало сессии:** прочитать `HANDOFF.md` → выбрать нужные доки по карте из `CLAUDE.md`.

**Конец сессии:** перезаписать `HANDOFF.md`, дополнить `DECISIONS.md` (если было решение),
отметить прогресс в `BACKLOG.md`. Не полагаться на `/compact` — сессия одноразовая,
файл вечен.

**Восстановление после `/clear`** — команда `.claude/commands/catchup.md`:

```markdown
Восстанови контекст. Прочитай HANDOFF.md, затем все файлы, изменённые
в текущей ветке относительно main. Кратко: что сделано, что осталось.
Изменённые файлы: !`git diff --name-only main`
```

## Приложение. Промпт для нового проекта

Вставить в Claude Code в пустом репозитории:

```
Создай документацию проекта по стандарту из DOC_STANDARD.md (лежит в корне).

1. Прочитай DOC_STANDARD.md целиком.
2. Задай мне вопросы, которых не хватает: назначение проекта, стек, команды
   запуска/тестов, ключевые ограничения, план по фазам. Не додумывай.
3. Создай по шаблонам из стандарта:
   CLAUDE.md, HANDOFF.md, docs/SPEC.md, docs/ARCHITECTURE.md,
   docs/DECISIONS.md, docs/BACKLOG.md
4. Сделай симлинк: ln -s CLAUDE.md AGENTS.md
5. Создай .claude/commands/catchup.md по образцу из стандарта.
6. В DECISIONS.md сразу занеси ADR-001 — выбор стека, с альтернативами и причиной.
7. Разделы, для которых у меня пока нет данных, оставь с явной пометкой
   «TODO: заполнить владельцем» — не выдумывай содержание.
8. Проверь: CLAUDE.md < 200 строк, все ссылки на файлы существуют.
   Покажи git status и дерево созданных файлов.
```
